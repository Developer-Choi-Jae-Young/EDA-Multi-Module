#### 🌿 v2 - 단일 프로젝트 + 이벤트 기반 구조 (Event-Driven)
v1의 강한 결합도 문제를 해결하기 위해 **Spring Event**를 도입한 단계입니다.

* **EDA(Event-Driven Architecture)란?**
    * 상태의 변화(이벤트)를 발행(Publish)하고, 해당 이벤트에 관심 있는 수신자(Consumer)가 이를 처리하는 아키텍처입니다.
    * **느슨한 결합(Loose Coupling)**: 생성 주체와 소비 주체가 서로를 몰라도 되므로 시스템 간 의존성이 최소화됩니다.
    * **단일 책임 원칙(SRP)**: 주문 서비스는 '주문' 로직에만 집중하고, 이후의 재고 차감이나 알림 처리는 별도의 핸들러가 담당합니다.


* **구현 핵심**:
    * **Publisher**: `OrderService`에서 `ApplicationEventPublisher`를 통해 `InventoryDecrementEvent`를 발행합니다.
    * **Subscriber**: `InventoryEventHandler`가 `@EventListener`를 통해 이벤트를 수신하고 재고 차감 로직을 실행합니다.


* **코드 기반 비즈니스 흐름**:
    1. **주문 요청**: `OrderController`가 주문 정보를 받습니다.
    2. **이벤트 발행**: `OrderService`는 재고 시스템의 내부 구현을 모르는 상태로 "재고 차감 필요"라는 **이벤트만 발행**합니다.
    3. **관심사 분리**: 재고 부족 시 발생하느 예외(`BuyException`)나 재고 조회 로직은 모두 `InventoryEventHandler`가 담당하므로 `OrderService` 코드가 간결해집니다.


* **개선 사항**:
    * **로직의 분리**: 주요 비즈니스 로직(주문 등)과 부가 로직(알림, 로그, 통계 등)을 이벤트로 분리하여 관리합니다.
    * **의존성 제거**: 서비스 간의 직접적인 참조(`DIP` 위반 등)를 제거하여, 특정 기능 수정이 전체 시스템의 에러로 번지는 사이드 이펙트를 방지합니다.
    * **확장성**: 새로운 부가 기능이 필요할 때 기존 주문 로직을 수정하지 않고 새로운 이벤트 리스너를 추가하는 것만으로 기능을 확장할 수 있습니다.

### 💡 Deep Dive: Event Handling & Transaction Boundary

v2 구조에서는 이벤트 핸들러의 실행 시점을 제어하기 위해 두 가지 리스너를 구분하여 사용하고, 트랜잭션 경계를 명확히 관리합니다.

#### 1. @EventListener vs @TransactionalEventListener
이벤트가 발행되는 시점과 구독하는 시점의 트랜잭션 동기화 여부에 따라 선택합니다.

* **`@EventListener`**:
    * **동기적 실행**: 발행자(Publisher)와 동일한 트랜잭션 범위 내에서 실행됩니다.
    * **특징**: 리스너에서 예외가 발생하면 발행자의 트랜잭션도 함께 롤백됩니다. 강한 일관성이 필요할 때 사용합니다.
* **`@TransactionalEventListener`**:
    * **트랜잭션 상태에 따른 실행**: 발행자의 트랜잭션 상태(예: `AFTER_COMMIT`)에 따라 리스너 실행 여부를 결정합니다.
    * **특징**: 기본값인 `AFTER_COMMIT` 설정 시, 주문 로직이 완전히 성공(Commit)된 후에만 이벤트(알림 등)가 실행됩니다. 발행자 로직에 영향을 주지 않아 시스템 안정성이 높습니다.

#### 2. 트랜잭션 경계 (Transaction Boundary)
이벤트 기반 구조에서 데이터 정합성을 유지하기 위한 전략입니다.



* **경계 분리**: 주문 서비스의 트랜잭션이 종료된 후 이벤트를 실행함으로써, 부가 로직(알림 전송 등)의 실패가 메인 비즈니스 로직(주문 완료)을 취소시키지 않도록 격리합니다.
* **주의사항**: `AFTER_COMMIT` 단계의 리스너는 이미 트랜잭션이 완료된 상태이므로, 리스너 내부에서 DB를 수정하려면 반드시 **`@Transactional(propagation = Propagation.REQUIRES_NEW)`**를 사용하여 새로운 트랜잭션을 시작해야 합니다.
