## 🌿 v3 - 멀티 모듈 프로젝트 + 이벤트 기반 구조 (Multi-Module Project)

단일 프로젝트(Monolithic) 구조의 한계를 극복하고, 서비스의 확장성과 유지보수성을 극대화하기 위해 **멀티 모듈 아키텍처**를 도입했습니다.

### ❓ 멀티 모듈(Multi-Module)이란?
하나의 부모 프로젝트(Root Project) 아래에 여러 개의 독립적인 자식 모듈(Sub-Module)을 두어 관리하는 구조입니다. 단순히 폴더를 나누는 것을 넘어, 각 모듈이 **독립적인 빌드 단위**가 되며 필요한 모듈을 선택적으로 조합하여 실행할 수 있습니다.



### 🏗 모듈 구성 (Module Structure)
이미지상의 실제 프로젝트 구조에 따라 도메인별로 물리적 경계를 나누어 관리합니다.

* **`Common`**:
    * 모든 모듈에서 공통으로 사용하는 베이스 모듈입니다.
    * 전역 예외 처리(`Exception`), 공통 DTO, 유틸리티 클래스를 포함합니다.
* **`Order`**:
    * 서비스의 메인 진입점 역할을 하며 주문 프로세스를 담당합니다.
    * 주문 생성 시 `InventoryDecrementEvent`를 발행(Publish)하여 타 도메인과 소통합니다.
* **`Inventory`**:
    * 상품의 재고 수량 관리 및 차감/복구 로직을 포함합니다.
    * 발행된 이벤트를 구독(Subscribe)하여 실질적인 재고 정정 로직을 수행합니다.
* **`Product`**:
    * 상품의 마스터 정보(이름, 가격 등)를 관리하는 도메인입니다.
* **`Member`**:
    * 사용자 정보 및 구매자 관련 로직을 담당합니다.

---

### 🌟 멀티 모듈 도입의 장점

1.  **코드의 재사용성**: `Common` 모듈에 공통 로직을 집중시켜 중복 코드를 방지하고, 새로운 서비스 모듈 추가 시 기존 도메인 모듈을 쉽게 재사용할 수 있습니다.
2.  **도메인 간의 명확한 경계 (격리성)**: Gradle 설정을 통해 모듈 간 참조 관계를 제어합니다. 도메인 간의 무분별한 참조를 막아 계층적 설계와 높은 응집도를 유지합니다.
3.  **빌드 및 테스트 속도 향상**: 전체를 빌드할 필요 없이 변경된 특정 모듈만 부분적으로 빌드 및 테스트가 가능하여 개발 생산성이 향상됩니다.
4.  **기술 스택의 유연성**: 각 모듈에 필요한 라이브러리만 선택적으로 추가할 수 있어 어플리케이션이 가벼워집니다.

---

### 💡 핵심 학습 포인트: AutoConfiguration (설정 자동화)

멀티 모듈 환경에서는 각 도메인 모듈에 정의된 Bean이나 JPA 엔티티를 메인 모듈이 자동으로 스캔하지 못하는 이슈가 발생합니다.

* **문제 상황**: 메인 Application의 `@SpringBootApplication` 스캔 범위를 벗어난 하위 모듈의 설정이 무시됨.
* **해결 방법**:
    * 각 모듈별로 필요한 설정 클래스(`DataConfig`, `EventConfig` 등)를 작성합니다.
    * `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 파일에 해당 클래스를 등록합니다.
    * 이를 통해 모듈 간 의존성을 추가하는 것만으로 별도의 `@Import` 없이 설정이 자동 적용되도록 구현했습니다.

### ⚠️ v3의 한계: 데이터 정합성 이슈 (Concurrency Issue)
구조적 유연성은 확보했으나, **대량의 트래픽이 동시에 유입될 때 재고 수량이 일치하지 않는 문제**가 발생했습니다. 여러 트랜잭션이 동일한 재고 데이터에 동시에 접근하여 수정하는 과정에서 데이터 손실(Lost Update)이 발생하기 때문입니다.
