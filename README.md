## 🌿 v4 - 동시성 문제 해결 <낙관적 락 (Optimistic Lock)>

v3에서 발생했던 **Race Condition**(다수의 사용자가 동시에 동일 재고를 수정할 때 데이터가 덮어씌워지는 현상)을 해결하기 위해 JPA의 낙관적 락을 도입했습니다.

### ❓ 낙관적 락(Optimistic Lock)이란?
대부분의 트랜잭션이 충돌하지 않는다고 가정한 상태에서 진행하는 잠금 방식입니다. DB의 물리적인 Lock 기능을 사용하는 것이 아니라, JPA가 제공하는 **버전 관리 기능**을 사용하여 어플리케이션 레벨에서 정합성을 체크합니다.

---

### ⚙️ 구동 원리 (Mechanism)

JPA의 `@Version` 어노테이션을 엔티티에 추가하여 동작합니다.

1. **조회 (Read)**: 엔티티를 조회할 때 현재의 `Version` 값을 함께 읽어옵니다.
2. **수정 (Update)**: 데이터를 수정할 때 `WHERE` 절에 처음에 읽었던 버전을 조건으로 포함합니다.
    - `UPDATE INVENTORY SET QUANTITY = ?, VERSION = VERSION + 1 WHERE ID = ? AND VERSION = {최초 읽은 버전}`
3. **충돌 감지**:
    - 만약 다른 트랜잭션이 먼저 수정을 완료하여 DB의 버전이 올라갔다면, 수정 쿼리의 `WHERE` 조건이 맞지 않아 업데이트된 행(Row) 수가 0이 됩니다.
    - 이때 JPA는 **`OptimisticLockException`**을 발생시켜 트랜잭션을 롤백합니다.



---

### 📊 장점과 단점

| 구분 | 내용 |
| :--- | :--- |
| **장점** | - DB의 물리적 락을 잡지 않으므로 자원 점유가 없어 **성능상 이점**이 큽니다.<br>- 데드락(Deadlock) 발생 위험이 거의 없습니다.<br>- 충돌이 적은 시스템에서 가장 효율적인 동시성 제어 방식입니다. |
| **단점** | - **충돌 발생 시 후처리 로직**을 개발자가 직접 구현해야 합니다 (예: 재시도 로직).<br>- 충돌이 빈번하게 발생하는 환경(인기 상품 주문 등)에서는 재시도 비용으로 인해 오히려 성능이 저하될 수 있습니다. |

---

### 🛠 구현 포인트
* **Entity 설정**: `Inventory` 엔티티 내에 `@Version` 어노테이션이 붙은 필드 추가.
* **예외 핸들링**: 서비스 레이어 혹은 파사드(Facade) 레이어에서 `OptimisticLockException` 발생 시 일정 횟수만큼 **재시도(Retry)** 로직을 수행하도록 설계.

---

### 🔄 충돌 해결 전략: @Retry (재시도 로직)

낙관적 락은 충돌 발생 시 `OptimisticLockException`을 던지고 트랜잭션을 종료합니다. 하지만 단순히 에러를 뱉고 끝내는 대신, **성공할 때까지 몇 번 더 시도**하는 전략이 필요합니다.

#### 1. @Retry란?
* **개념**: 특정 예외가 발생했을 때 해당 메서드를 자동으로 다시 실행하는 기능입니다.
* **필요성**: 낙관적 락은 동시에 10명이 주문하면 1명만 성공하고 9명은 실패합니다. 이때 실패한 9명이 자동으로 다시 재고를 확인하고 주문을 시도하게 하여 사용자 경험을 개선합니다.

#### 2. 구동 원리
Spring에서는 주로 `Spring Retry` 라이브러리를 활용하여 AOP 방식으로 구현합니다.

1. **예외 감지**: 메서드 실행 중 지정한 예외(`OptimisticLockException`)가 발생하면 가로챕니다.
2. **지연(Backoff)**: 즉시 재시도하면 다시 충돌할 확률이 높으므로, 짧은 시간(예: 100ms) 대기합니다.
3. **재실행**: 새로운 트랜잭션을 시작하여 로직을 다시 수행합니다.
4. **최종 실패**: 설정한 최대 재시도 횟수(maxAttempts)를 초과하면 최종 예외를 던집니다.

---

#### 3. @Retry의 장단점

| 구분 | 내용 |
| :--- | :--- |
| **장점** | - 비즈니스 로직 수정 없이 **어노테이션 설정만으로 간편하게** 재시도 구현 가능.<br>- 일시적인 네트워크 오류나 동시성 충돌 상황을 부드럽게 복구. |
| **단점** | - **무한 재시도 위험**: 설정이 잘못되면 무한 루프에 빠지거나 시스템 자원을 고갈시킴.<br>- **성능 저하**: 충돌이 극심할 경우 대기 시간(Backoff)과 재시도 횟수만큼 응답 속도가 느려짐. |

---

#### 4. 코드 구현 예시
```java
@Service
public class OrderFacade {
    private final OrderService orderService;

    @Retryable(
        retryFor = {OptimisticLockException.class}, 
        maxAttempts = 3, 
        backoff = @Backoff(delay = 100)
    )
    public void buyWithRetry(BuyOrderDto dto) {
        orderService.buy(dto);
    }

    @Recover
    public void recover(OptimisticLockException e, BuyOrderDto dto) {
        // 3번 모두 실패했을 때의 후처리 로직 (예: 사용자에게 알림)
    }
}
```

## 🧪 동시성 테스트 및 검증 (Concurrency Test)

동시성 제어 로직이 실제로 작동하는지 확인하기 위해 `CountDownLatch`와 `ExecutorService`를 활용하여 멀티스레드 테스트를 수행했습니다.

### 🛠 테스트 주요 도구
* **`ExecutorService`**: 병렬 작업을 수행할 스레드 풀을 생성합니다. (예: 10개~100개의 스레드 생성)
* **`CountDownLatch`**: 모든 스레드가 작업을 완료할 때까지 메인 스레드를 대기시켜, 테스트 결과가 정확히 집계되도록 보장합니다.
* **`AtomicInteger`**: 멀티스레드 환경에서 안전하게 성공/실패 횟수를 카운트합니다.

### 📋 주요 테스트 시나리오

#### 1. 동시성 문제 재현 (Race Condition)
* **상황**: 10개의 스레드가 동시에 각각 2개씩 주문 시도 (총 20개 주문 시도).
* **기대 결과**: 재고가 10개뿐이므로, 동시성 제어가 없다면 재고가 음수가 되거나 판매된 수량과 남은 재고의 합이 초기 재고(10개)와 맞지 않음.
* **검증**: `assertEquals(초기재고, 판매량 + 남은재고)`를 통해 데이터의 원자성을 확인합니다.

#### 2. 재고 부족 상황의 부분 성공 테스트
* **상황**: 재고가 10개일 때, 10명이 동시에 3개씩 구매 시도 (총 30개 요청).
* **기대 결과**: 선착순으로 딱 3명만 성공하고, 나머지 7명은 반드시 실패해야 함.
* **검증**: `successCount <= 3` 조건을 통해 초과 판매 방지를 확인합니다.

#### 3. 극한의 동시성 테스트 (Extreme Test)
* **상황**: 100개의 요청을 동시에 발생시켜 시스템의 안정성 확인.
* **검증**: 어떤 상황에서도 **최종 재고는 0 이상**이어야 하며, 데이터 정합성이 깨지지 않아야 함.

---

### 🔍 테스트 코드 핵심 로직
```java
// 모든 스레드가 동시에 출발하도록 대기
CountDownLatch latch = new CountDownLatch(threadCount);

for (int i = 0; i < threadCount; i++) {
    executorService.submit(() -> {
        try {
            orderService.buy(dto); // 주문 시도
            successCount.incrementAndGet();
        } catch (Exception e) {
            failCount.incrementAndGet(); // 실패 집계
        } finally {
            latch.countDown(); // 완료 신호
        }
    });
}

latch.await(); // 모든 요청이 끝날 때까지 대기 후 결과 검증
```

### ⚠️ v4의 한계
재고 차감과 같이 충돌이 빈번하게 일어나는 핵심 비즈니스 로직에서는 낙관적 락의 **'실패 후 재시도'** 방식이 시스템 부하를 가중시킬 수 있습니다. 이를 더 확실하게 제어하기 위해 **v5에서는 DB의 물리적 락을 사용하는 비관적 락**을 실습합니다.
